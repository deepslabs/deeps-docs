A DHC keyring device is a physical machine that runs the DeepS keyring software in an Intel SGX environment and manages secret keys through multi-party computation (MPC).

## Basic Concepts

1. **Device Secret Key**: An SGX-derived secret key that represents the hardware identity. The key is obtained through the Intel SGX `get_secret_key` interface with the `0x0002` policy, which corresponds to _SGX\_KEYPOLICY\_MRSIGNER_.
2. **DeviceId**: The public key associated with the **Device Secret Key**. It is registered on-chain.
3. **Enclave Secret Key**: A second identity key that represents a specific SGX environment running specific code. The key is obtained through the Intel SGX `get_secret_key` interface with the `0x0001` policy, which corresponds to _SGX\_KEYPOLICY\_MRENCLAVE_. It is unique to the combination of hardware and enclave code.
4. **EnclaveId**: The public key associated with the **Enclave Secret Key**. It is registered on-chain and mapped to the corresponding **DeviceId**.
5. **EnclaveHash**: A unique hash of the enclave code, generated when the enclave is built and included in the SGX attestation evidence. DeepS uses this hash to verify that every device is running an approved code version.
6. **MrSigner**: The measurement of the identity used to sign the enclave. The signing identity is embedded when the Docker image is built, allowing operators to verify the enclave publisher.
7. **Owner**: An on-chain account designated by the hardware operator. Rewards earned by the device are sent to this account.

## Device States

1. **Working**: The owner must provide sufficient on-chain collateral for the device and submit a `join_service` transaction. The device then performs MPC, RingVRF, heartbeat, and consensus tasks, for which the **Owner** receives additional rewards. The owner **SHOULD NOT** shut down the hardware or keyring service while the device is in this state.
2. **Exiting**: The owner can submit an `exit_service` transaction. The device stops joining new committees, waits until it has left all existing committees, and then automatically submits a `report_standby` transaction. The owner **SHOULD NOT** shut down the hardware or keyring service while the device is in this state.
3. **Standby**: This is the default state after a device is registered. A device returns to **Standby** after completing all assigned work and successfully reporting its standby status. In this state, it sends heartbeats but does not participate in service checks. The owner **CAN** shut down the hardware or keyring service.

## Dependency Service: Monitor

The monitor is a dependent service that also runs in an SGX environment. It continuously monitors each supported chain, synchronizes blocks, and verifies block correctness.

When a device receives a **Sign** task for a cross-chain transaction, it asks the monitor to verify that the source transaction exists.

Each device must use one of the following monitor modes:

1. **Local**: The operator runs a dedicated monitor for the device and registers it on-chain. This mode provides higher rewards.
2. **Public**: The device obtains information from an official public monitor. This is the default mode and provides lower rewards.

The device then:

1. Binds its monitor information on-chain during registration.
2. Periodically checks the synchronization status of monitored chains. In **Local** mode, the device compares its local monitor with the **Public** monitor. If the local block height falls behind, the device does not accept work and may be penalized for disrupting **Sign** tasks.
3. Verifies source-chain transactions through the monitor before signing cross-chain transactions.

### Committee

A device ultimately serves one or more **Committees**. The following concepts describe how committees operate.

A **Committee** is a group of members that use MPC to maintain a secret key for asset management and message signing. For resilience, a committee can contain multiple forks of MPC participants. A device uses a temporary identity to join one or more forks, although it typically joins only one.

The committee's lifetime is defined as **GlobalEpoch**:

1. **EpochBlocks**: The total number of blocks in the **GlobalEpoch**.
2. **ApplyBlocks**: The blocks during which a committee epoch change (**KeyHandover**) is applied.
3. **RvrfBlocks**: The blocks during which devices submit RingVRF proofs to generate temporary identities for the epoch.
4. **ReserveBlocks**: Blocks reserved for future use.
5. **ChangeBlocks**: The blocks during which committees perform **KeyHandover**. Devices report successful results on-chain.

At each **GlobalEpoch** transition, committee members hand over their secret-key shares to the next set of members.

## Device Tasks

When a device enters the **Working** state, on-chain events can assign it the following tasks:

1. **RingVRF**: The device generates a RingVRF proof and a temporary identity for the current **GlobalEpoch**. This identity may be selected to perform work for one or more committees.
2. **KeyGenerate**: Selected devices use their temporary identities to perform MPC and generate a committee's secret-key shares and public key. One of the identities signs and reports the result.
3. **KeyHandover**: During each **GlobalEpoch**, a committee uses MPC to transfer secret-key shares from the previous epoch's identities to the new identities. After a successful handover, the chain emits `pallet_committee::event::ApplyEpochChange` during **ApplyBlocks**. The previous identities delete their shares, and the new identities assume the committee's MPC responsibilities. During committee creation, fork 0 performs **KeyGenerate** and then uses **KeyHandover** to distribute shares to the other forks.
4. **Sign**: Various on-chain events, such as `pallet_channel::event::NewTransaction`, trigger this MPC task. The identities selected for the current epoch process the request.

## Further Reading

#### A. Device Consensus

There are two important states on chain:

1. **snapshots**: The collection of **EnclaveIds** for **Working** devices. It is updated at the start of each **GlobalEpoch**.
2. **candidates**: The collection of temporary identities generated through device **RingVRF** proofs. It is updated at the end of the **RvrfBlocks** period in each **GlobalEpoch**.

Devices must agree on the **snapshots** and **candidates** state used for committee **KeyGenerate** and **KeyHandover** tasks. This consensus **SHOULD** be confirmed during every **GlobalEpoch**.

This consensus protects against rollback-based attacks. Under normal operation, a committee's secret-key shares are distributed across devices, and SGX protects each device's data. A malicious operator controlling multiple devices could nevertheless attempt a **Database Backup Attack** to recover a committee's complete secret key.

Device tasks are driven by on-chain events, but the owner configures the node that supplies those events. A malicious owner could therefore:

1. Back up each device database during every **GlobalEpoch**.
2. Wait until the next committee epoch change, when devices reveal their identities to claim rewards.
3. Determine whether the operator's randomly selected devices collectively hold enough shares to recover a particular committee key.
4. Restore the backed-up databases and supply fabricated events and state, such as **snapshots** and **candidates**, causing the devices to run **KeyHandover** and transfer shares to identities controlled by the operator.

**Consensus Process**

**CourtMember**: Devices in the confirmed **snapshot** form the court. Court membership is determined by consensus during the previous epoch.

1. At the start of a **GlobalEpoch**, the **snapshot** is updated. The previous epoch's **CourtMembers** vote on the new snapshot. If more than half approve it, the snapshot is confirmed for the new epoch and its members become the current **CourtMembers**. Otherwise, the previous epoch's **CourtMembers** become the new **snapshot**, and court membership remains unchanged.
2. At the end of **RvrfBlocks**, the current **CourtMembers** vote on the **candidates** state. If more than half approve it, the state is confirmed and subsequent **KeyHandover** tasks select members from **candidates**. Otherwise, **candidates** is cleared and devices do not perform **KeyGenerate** or **KeyHandover** tasks during that epoch.
